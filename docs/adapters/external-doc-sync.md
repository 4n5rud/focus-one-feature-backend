# 외부 API 문서 동기화 어댑터 (예시: Notion) — 선택

[branch-workflow.md](../rules/branch-workflow.md) 15단계(PR 생성) 이후에 걸리는 선택 훅이다.
팀 전체가 참조하는 확정 API 스펙 문서(Notion, Confluence 등)를 별도로 운영하는 경우에만
필요하다 — 안 쓰는 팀은 이 어댑터 자체를 생략한다.

## 언제 반영하는가
- **PR이 통합 브랜치에 머지된 게 확인된 뒤에 진행한다**(머지 전 상태를 미리 적어두지
  않는다). 통합 브랜치의 정의는 [branch-strategy.md](./branch-strategy.md) 참고.
- 이렇게 머지 후로 미루는 이유: 이 문서는 팀 전체가 참조하는 확정 스펙이다. PR 리뷰로
  계약이 바뀔 가능성이 남아있는 동안 미리 반영하면, 팀원이 아직 확정되지 않은 스펙을
  보고 작업할 위험이 있다. 반면 [api-client-collection.md](./api-client-collection.md)
  (Postman 등)는 개발자 본인의 테스트 도구이므로 QA 시점에 바로 반영해도 무방하다 — 두
  훅의 반영 시점이 다른 이유다.
- 그 PR에서 실제로 추가/변경된 엔드포인트만 다룬다. 이 규칙이 생기기 전에 머지돼 아직
  문서화되지 않은 엔드포인트를 발견하면, 임의로 다 채우지 말고 팀에 먼저 확인한다.

## 예시: Notion 데이터베이스 필드 작성 규칙
- **엔드포인트**: `{Method} {경로}` (예: `PATCH /api/v1/orders/{code}/approve`)
- **Method / 도메인 / 상태 / 인증 필요**: select/checkbox 필드의 기존 옵션을 그대로 쓴다.
  해당하는 도메인 옵션이 없으면 새로 추가한다.
- **API 코드**: 도메인 접두사 + 순번(예: `ORDER_001`, `ORDER_002`, ...). 이 코드는 앱의
  에러 코드 enum 값과는 별개의, 이 문서 안에서만 쓰는 식별 번호다 — 같은 도메인 안에서
  엔드포인트가 실제로 구현/머지된 순서대로(기획 순서가 아니라) 번호를 매긴다.
- **Request / Response**: 실제 예시 값이 아니라 **JSON 형식(필드명 + 타입/설명)만** 적는다.
  ```json
  {
    "orderDate": "string (yyyyMMdd)",
    "deliveryType": "PICKUP | COURIER | CUSTOM"
  }
  ```
  `"orderDate": "20260814"`처럼 실제 값을 넣지 않는다 — 기획서
  (`docs/domain/{도메인명}/{이슈번호}-...md`)에는 실제 예시가 있으니 거기서 확인하면 되고,
  여기는 스키마 참고용이다.
  - 특이사항(예: "CUSTOM일 때만 필수", "실패 시 재시도 규칙")이 있으면 JSON 블록 다음
    **한 줄을 띄우고** 그 아래에 적는다.
- **예외/오류 처리 / 비고**: 서술형 문단으로 쓰지 않는다 — 표 칸이 좁아서 문단이 깨진다.
  **번호를 매긴 목록**으로 정리하고, 각 항목은 `<br>`로 구분한다(Notion DB의 기존 줄바꿈
  렌더링 방식). 형식 예:
  ```
  1. 403 ORDER_004 OWNER_MISMATCH - 호출한 사용자가 주문 소유자가 아님<br>
  2. 409 ORDER_005 ALREADY_PROCESSED - 이미 처리된 주문<br>
  3. 404 ORDER_006 ORDER_NOT_FOUND - 존재하지 않는 code
  ```

## 이 훅을 다른 도구로 교체할 때
Confluence, GitBook, 사내 위키 등 어떤 도구를 쓰든 위 세 가지(반영 시점, 이 문서 안에서만
쓰는 식별 코드 규칙, 예시 값 대신 스키마만 적는 원칙)만 유지하면 된다.
