# 브랜치 전략 어댑터 (예시: 3단계 — main/staging/dev)

[branch-workflow.md](../rules/branch-workflow.md)가 참조하는 "🔌 브랜치 전략" 훅이다. 이
문서를 프로젝트가 실제로 쓰는 전략으로 통째로 교체해서 쓴다.

## 이 문서가 정의해야 하는 것
- **통합 브랜치**가 무엇인가 (feature 브랜치들이 가장 먼저 모이는 곳)
- 보호해야 할 브랜치와 그 이유 — 직접 push를 막는 이유가 리뷰 규율 유지인지, 배포 파이프라인
  트리거 때문인지에 따라 규칙의 무게가 달라진다
- default 브랜치가 통합 브랜치와 같은지 다른지 — 다르면 PR의 `closes #N` 자동 종료가 언제
  발동하는지가 달라진다 ([pr-template.md](../rules/pr-template.md) 참고)

## 예시 A. 3단계 브랜치 전략 (main / staging / dev)
- `main`: 실제 운영 배포 대상, default 브랜치.
- `staging`: 배포 전 최종 검증 환경. CI/CD가 붙어 있어 push하면 즉시 배포 파이프라인이 돈다.
- `dev`: 로컬 feature 브랜치들이 모이는 통합 지점. 배포 트리거는 붙어있지 않다.

### 🚫 dev 직접 푸시 금지
- **`dev`에는 어떤 커밋도 직접 push하지 않는다. 항상 브랜치를 분기해 PR로 머지한다.** 직접
  push를 금지하는 이유는 배포 차단이 아니라 **히스토리/리뷰 규율 유지**다 — 코드 변경이든
  문서(기획서)뿐인 변경이든 예외 없이 PR을 거쳐야 리뷰·커밋 히스토리가 남는다.
- 기획서(2단계) 커밋도 예외가 아니다. 7단계에서 만드는 기능 브랜치의 첫 커밋으로 넣거나,
  별도 `docs/#{이슈번호}-...` 브랜치를 분기해 PR로 머지한다.

### 🚫 staging 직접 푸시 금지
- **`staging`에는 어떤 커밋도 직접 push하지 않는다.** 직접 push하면 그 즉시 실제 배포
  파이프라인이 돈다. `staging`은 오직 `dev → staging` **승격 PR**을 통해서만 갱신한다 —
  승격 PR은 `dev`에서 이미 검증된 커밋을 옮기는 것뿐이라 별도 이슈/기획서 없이 진행 가능하다.

### PR 머지 & 이슈 종료
- feature PR은 `dev`로 머지된다. `dev`는 default 브랜치가 아니므로 GitHub의 `closes #N`
  자동 종료는 이 시점에 발동하지 않는다(자동 종료는 default 브랜치로 머지될 때만 동작한다).
  머지 직후 관련 이슈를 `gh issue close`로 직접 닫는다.

## 예시 B. 트렁크 기반 (main 하나만)
- feature 브랜치를 `main`(= default = 통합 브랜치)에서 분기해 PR로 바로 머지한다. 별도
  승격 단계가 없다.
- 위 "dev/staging 직접 푸시 금지" 절은 통째로 걷어내고, `main` 직접 push 금지 규칙만
  유지한다.
- `main`이 default 브랜치이므로 `closes #N`이 머지 시점에 자동으로 발동한다 — 이슈를
  수동으로 닫을 필요가 없다.

## 이 훅을 다른 전략으로 교체할 때
GitFlow, 릴리스 브랜치 기반 등 다른 전략을 쓴다면 위 두 예시의 구성 요소(통합 브랜치 정의,
보호 브랜치와 그 이유, 이슈 자동 종료 시점)만 그대로 채워 넣으면 된다 — 이 세 가지만
명시돼 있으면 [branch-workflow.md](../rules/branch-workflow.md)의 나머지 단계는 전략이
바뀌어도 그대로 동작한다.
