# DB 마이그레이션 버전 어댑터 (예시: Flyway)

[branch-workflow.md](../rules/branch-workflow.md) 2단계(기획서 생성)의 "데이터 모델 변경"
절이 참조하는 "🔌 마이그레이션" 훅이다. DB 마이그레이션 도구가 다르면 이 문서를 그 도구
기준으로 통째로 교체한다. DB 스키마 변경이 없는 프로젝트라면 이 어댑터 자체가 필요 없다.

## 예시: Flyway — 타임스탬프 버전
새로 추가하는 마이그레이션은 순번(`V1`, `V2`, ...) 대신 타임스탬프 버전을 쓴다.

```
V{yyyyMMddHHmmss}__{설명}.sql
```

예: `V20260824151700__add_user_last_login_at.sql`

- 타임스탬프는 팀이 합의한 기준 시간대(예: KST)로 통일한다. 로컬 머신 시계가 그 시간대가
  아닐 수 있으므로(WSL/Docker, 해외 위치 등은 기본값이 UTC인 경우가 많다) OS 타임존
  설정에 기대지 말고 명시적으로 변환해서 얻는다.
  - Node(OS 타임존 설정과 무관하게 항상 정확함, 아래는 UTC+9 기준 예시):
    `node -e "console.log(new Date(Date.now()+9*3600*1000).toISOString().slice(0,19).replace(/[-T:]/g,''))"`
  - PowerShell(KST 예시): `[TimeZoneInfo]::ConvertTimeBySystemTimeZoneId((Get-Date), 'Korea
    Standard Time').ToString('yyyyMMddHHmmss')`
  - bash의 `TZ=... date ...`처럼 OS/셸의 타임존 데이터베이스에 의존하는 방식은 환경에 따라
    잘못된 값(예: UTC)을 낼 수 있으니, 반드시 얻은 값이 실제 기준 시각과 맞는지 눈으로
    한 번 확인한다.
- 브랜치 생성 시점에 미리 번호를 확정하지 않는다 — 실제로 마이그레이션 파일을 커밋하는
  순간의 타임스탬프를 쓴다.

### 왜 순번을 버리는가
여러 브랜치가 동시에 진행되는 협업 환경에서 "다음 빈 번호"를 각자 브랜치 기준으로
판단하는 순번 방식은, 병합 순서가 브랜치 생성 순서와 다르면 버전이 겹친다 — 서로 다른
시점에 분기된 두 브랜치가 우연히 같은 순번을 매기면, 나중에 머지되는 쪽에서 마이그레이션
도구가 버전 충돌을 일으켜 컨텍스트 로딩(빌드/부팅) 자체를 실패시킬 수 있다. 타임스탬프
버전은 Flyway가 팀 개발용으로 공식 권장하는 방식이고, 같은 초에 두 마이그레이션이 동시에
커밋되는 경우가 아니면 충돌 가능성이 사실상 없다.

### 기존 순번 버전은 그대로 둔다
이미 각 환경(로컬/CI/staging)에 적용된 이력이 있는 순번 방식 버전은 재번호하지 않는다 —
되돌리면 각 환경의 마이그레이션 이력 테이블과 어긋나 더 큰 문제가 된다. Flyway는 버전을
점(`.`)/밑줄(`_`)로 나눠 숫자로 비교하므로, 순번(예: `17`)과 타임스탬프(예:
`20260824151700`)가 섞여 있어도 항상 타임스탬프 쪽이 더 큰 값으로 정렬돼 문제없이 공존한다.

## 이 훅을 다른 도구로 교체할 때
Liquibase/Prisma Migrate/Alembic 등 다른 도구를 쓰면, 그 도구가 버전을 비교하는 방식(순번
기반인지 타임스탬프 기반인지)을 확인하고 위와 같은 원리(병렬 브랜치에서 번호가 겹치지
않게 하는 규칙)로 대체한다.
