# API 클라이언트 컬렉션 어댑터 (예시: Postman) — 선택

[branch-workflow.md](../rules/branch-workflow.md) 10단계(QA) 직후에 걸리는 선택 훅이다.
팀이 Postman/Insomnia 같은 도구로 API 요청 컬렉션을 공유하는 경우에만 필요하다 — 안 쓰는
팀은 이 어댑터 자체를 생략한다.

## 언제 반영하는가
- QA에서 실제 서버로 검증한 요청들을 바탕으로, PR 생성 전에 이번에 추가/변경된 엔드포인트를
  컬렉션에 반영한다. QA 때 이미 만든 요청을 재사용하면 되므로 별도 작업이 아니라 QA의
  연장선으로 처리한다.
- PR 리뷰로 엔드포인트 계약이 바뀌면, 머지 직전에 컬렉션이 최종 계약과 일치하는지 다시
  확인한다. 어긋나 있으면 머지 전에 갱신한다.
- 워크스페이스/API 키 같은 인증 정보는 리포지토리의 `.env`(gitignore 대상)에 두고, 실제
  키 값을 문서나 커밋에 남기지 않는다.

## 예시: Postman 컬렉션 구조
### 최상위 = 엔드포인트 1개당 항목 1개
`{프로젝트명} - {도메인} API` 컬렉션 최상위에는 **실제 구현된 엔드포인트 1개당 항목 1개**만
둔다. 로그인처럼 그 엔드포인트를 테스트하기 위한 사전 준비 흐름이나, 에러 케이스 모음,
여러 요청을 잇는 시나리오는 최상위 엔드포인트 목록과 섞지 않고 **별도 하위 폴더**(예:
"사전 준비", "에러 케이스")로 분리한다.

- 예: `Shop - Order API`는 최상위에 "주문 생성"/"주문 취소"/"주문 조회" 3개 항목만 두고,
  로그인/토큰 준비는 "사전 준비" 폴더, 403/409/404/400/401 케이스는 "에러 케이스" 폴더로
  분리한다.

### 기능(이슈)별 검증 폴더
이번 이슈에서 추가/변경한 엔드포인트를 처음부터 끝까지 확인할 수 있는 요청들을, 실행 순서
그대로 모은 전용 폴더를 하나 만든다. 폴더 이름은 뭘 확인하는 폴더인지 한눈에 알 수 있게
간단히 쓴다. 이 폴더 안에는 사전 준비(로그인 등)부터 실제 신규 엔드포인트 호출까지 전부
순서대로 넣는다.

- 예: 주문 생성 API를 추가했다면 "주문 생성 확인" 폴더를 만들고 그 안에 로그인 → 장바구니
  담기 → 주문 생성을 순서대로 담는다.
- 최상위 엔드포인트 목록/"사전 준비"/"에러 케이스" 폴더와는 별개로 유지한다 — 그 폴더들은
  도메인 전체 구조 정리용이고, 이 폴더는 이번 이슈 하나만 빠르게 검증하기 위한 것이다.

## 이 훅을 다른 도구로 교체할 때
Insomnia, Bruno, 사내 API 테스트 도구 등 어떤 도구를 쓰든 위 두 원칙(엔드포인트 1개당
항목 1개 + 이슈별 검증 폴더)만 유지하면 된다.
