# 프로젝트 최초 설정 — 어댑터 확정 인터뷰

이 하네스를 새 프로젝트에 처음 적용할 때, 또는 `docs/adapters/*.md`에 예시 내용(Java/
Gradle/Flyway 등)이 그대로 남아있는 걸 발견했을 때 반드시 거치는 단계다.
[branch-workflow.md](./branch-workflow.md) 0단계보다 먼저 실행한다.

## 왜 물어보고 시작하는가
어댑터 문서에는 도구 예시가 채워져 있어서, 그대로 두면 실제 프로젝트와 맞지 않는 규칙
(Java 문법, Flyway 타임스탬프 등)을 그대로 따르게 될 위험이 있다. 코드베이스를 스캔해서
"아마 이 스택이겠지"라고 추측하고 조용히 넘어가지 않는다 — 스택 추측이 틀리면 이후 모든
단계(코드 스타일, 테스트, 마이그레이션)가 잘못된 규칙 위에서 진행된다. **반드시 구조화된
선택형 질문**(예: Claude Code의 AskUserQuestion 도구 — 선택지 2~4개 제시)으로 사용자에게
확인받는다.

## 언제 실행하는가
- 이 하네스가 설치된 프로젝트에서 처음으로 기능 구현/버그 수정 요청을 받았을 때.
- 또는 `docs/adapters/` 안의 파일이 여전히 이 저장소의 원본 예시(Java/Gradle/Checkstyle/
  JUnit5/Flyway 등 특정 키워드)를 담고 있는 게 확인될 때.
- 이미 어댑터가 실제 값으로 채워져 있다면(예시 문구가 하나도 없으면) 다시 묻지 않는다 —
  스택이 바뀌었다고 사용자가 먼저 말하는 경우에만 다시 인터뷰한다.

## 무엇을 묻는가
아래 항목을 **구조화된 선택형 질문**(선택지를 먼저 제시하고 그중에서 고르게 하는 형식,
필요하면 "직접 입력" 옵션 포함)으로 확인한다. "어떤 스택 쓰세요?" 같은 자유 서술형 질문
하나로 뭉뚱그리지 않는다 — 어댑터 개수만큼 구체적으로 나눠서 묻는다.

1. **브랜치 전략** ([branch-strategy.md](../adapters/branch-strategy.md)) — 예: "3단계
   (main/staging/dev)" vs "트렁크 기반(main 하나)" vs "직접 설명".
2. **코드 스타일/린터** ([code-style.md](../adapters/code-style.md)) — 프로젝트의 실제
   언어와 린터(예: "Java + Checkstyle", "TypeScript + ESLint", "Python + Ruff",
   "직접 입력").
3. **테스트 프레임워크** ([test-convention.md](../adapters/test-convention.md)) — 예:
   "JUnit5", "Jest/Vitest", "Pytest", "직접 입력".
4. **DB 마이그레이션 도구** ([migration-convention.md](../adapters/migration-convention.md)) —
   예: "Flyway", "Liquibase", "Prisma Migrate", "해당 없음(DB 마이그레이션 없음)".
5. **선택 어댑터 사용 여부**(다중 선택) — 외부 API 문서 동기화(Notion 등), API 클라이언트
   컬렉션(Postman 등), 자동 코드 리뷰 봇(CodeRabbit 등) 각각 쓸지 말지.

## 답변 반영
- 답변을 대화에만 남기지 않고, **그 자리에서 해당 어댑터 파일을 실제 값으로 고쳐 쓴다**
  (예시 문구를 삭제하고 답변 내용으로 대체한다). "나중에 채우겠다"며 예시를 남겨두고
  넘어가지 않는다.
- 4번 항목이 "해당 없음"이면 `migration-convention.md` 파일 자체를 삭제한다.
- 5번에서 안 쓰기로 한 선택 어댑터 파일은 삭제하고, [branch-workflow.md](./branch-workflow.md)의
  "훅 포인트 요약" 표에서도 해당 줄을 지운다.
- 이 인터뷰는 한 번 하면 끝이다 — 두 번째 기능 요청부터는 이미 채워진 어댑터를 그대로
  따르고, 다시 묻지 않는다.

## 기획 단계에서도 ask 형식을 우선한다
어댑터 확정뿐 아니라, [branch-workflow.md](./branch-workflow.md) 2~6단계(기획서 작성/
검토)에서 사용자에게 판단을 구할 때도 서술형으로 길게 묻기보다 **선택지를 먼저 제시하는
구조화된 질문 형식**을 우선 사용한다. 예: "페이지네이션을 이번 범위에 넣을까요, 다음으로
미룰까요?"처럼 구체적 선택지 2개 이상과 각각의 트레이드오프를 같이 제시하고 고르게 한다.
다만 사용자가 이미 방향을 정해서 요청한 경우, 또는 선택지로 구조화하기 어려운 열린 질문
(예: "이 기능이 왜 필요한가요?")까지 억지로 선택형으로 바꾸지는 않는다.
