# 진행 상태 추적 & 동시 진행 제한

[branch-workflow.md](./branch-workflow.md)를 따라 작업할 때 지켜야 하는 두 가지 구조적
규칙 — "한 번에 하나의 기능만 진행한다"와 "진행 상태를 GitHub 이슈로 외부화한다" — 를
다룬다. 두 규칙은 서로 전제를 공유한다: 진행 상태를 이슈 체크리스트로 외부화해두기
때문에 세션이 끊겨도 "지금 어느 이슈가 어디까지 진행됐는지"를 대화 기록 없이 복원할 수
있고, 그래야 "한 번에 하나만" 규칙을 세션이 끊기는 상황에서도 실제로 지킬 수 있다.

## 🚨 한 번에 하나의 기능만 (한 이슈, 한 브랜치)
- 이 워크플로우는 항상 "이슈 1개 ↔ 브랜치 1개 ↔ 기능 1개"만 동시에 진행한다.
- 진행 중인 이슈(0~15단계 중 어느 단계든)가 완전히 끝나기 전에는, 사용자가 다른 기능을
  언급하거나 "가능하면 지금부터 넣어달라"고 하더라도 새 이슈의 기획서 작성/브랜치 생성/구현을
  시작하지 않는다.
- 새 기능 요청이 들어오면: 진행 중인 이슈가 있다는 것을 알리고, 이슈만 생성해 백로그에
  기록해둔 뒤(기획서 작성은 보류), 현재 이슈가 끝난 뒤에 순서대로 착수한다.
- ⚠️ **단, "이런 기능도 나중에 필요할 거다"처럼 현재 이슈의 설계 판단을 돕기 위한 맥락 설명은
  이슈 생성 대상이 아니다.** 명시적으로 "이슈로 만들어줘"라고 하거나, 누가 봐도 독립된 기능
  요청일 때만 백로그 이슈를 만든다. 애매하면 먼저 "이거 이슈로 만들어둘까요?"라고 물어본다.
- QA 중(9~13단계) 발견된 버그는 새 이슈를 파지 않고 같은 브랜치에서 고친다. 새 이슈는
  ① 머지 후 발견된 회귀, ② 기획서 범위 밖의 스코프 크립(8단계 참고), 이 두 경우에만 만든다.
- 🔌 통합 브랜치를 상위 브랜치로 승격하는 PR(예: `dev → staging`)이 있는 브랜치 전략이라면,
  그 승격 PR도 이 규칙의 적용 대상이다. 다만 승격 PR은 `dev`에서 이미 개별 이슈/기획서/QA를
  거쳐 검증된 커밋을 그대로 옮기는 것뿐이라, 그 자체로 별도 이슈나 기획서를 새로 만들 필요는
  없다. 브랜치 구조는 [adapters/branch-strategy.md](../adapters/branch-strategy.md) 참고.

## 📋 진행 상태 추적 (외부화)
- 모델의 기억이 아니라 **레포 상태**로 진행 단계를 검증한다. 1단계에서 이슈를 생성할 때,
  이슈 본문에 0~15단계 체크박스를 전부 포함시키고, 각 단계가 끝날 때마다 그 이슈에서
  해당 체크박스를 갱신한다.
- 세션이 끊기거나 새로 시작하는 경우, 진행 중인 이슈가 있으면 그 이슈의 체크박스 상태를
  먼저 읽어서 어디까지 진행됐는지 확인한 뒤 이어간다. 대화 기록에 의존하지 않는다.
- 0단계에서, 직전에 닫힌 이슈가 있다면 그 이슈가 실제로 PR 머지까지 완료됐는지 확인한다.
  안 됐으면 새 이슈 착수보다 먼저 그것부터 마무리한다.
