# 코드 리뷰 컨텍스트 격리 규칙

[branch-workflow.md](./branch-workflow.md) 9단계(코드 리뷰)에서 리뷰 에이전트를 어떻게
띄우는지 다룬다. 리뷰 결과를 어떤 형식/파일로 남기는지는
[code-review-template.md](./code-review-template.md)를 따로 참고 — 이 문서는 "누가 어떻게
리뷰하는가", 그 문서는 "리뷰 결과를 어떻게 기록하는가"로 대상이 다르다.

## 왜 직접 리뷰하지 않는가
기능 구현이 끝나면 QA 전에 diff를 리뷰한다. **직접 리뷰하지 않고, 별도 에이전트를 하나
띄워 `code-review` 스킬을 등록시킨 뒤 그 에이전트에게 리뷰를 맡긴다** — 구현한 사람이
스스로 검토하면 놓치는 게 생기므로, 구현 맥락이 없는 새 에이전트가 diff만 보고 독립적으로
점검하게 한다.

## 컨텍스트 격리를 실제로 지킨다
이 에이전트에게는 diff, 기획서, code-review 스킬만 전달한다. 구현 과정의 대화 기록·추론·
가정은 넘기지 않는다. 구현자의 편향을 물려받으면 "독립 리뷰"라는 목적 자체가 무너진다.

## 확인 범위
기획서 범위를 벗어난 변경이 없는지, 기존 컨벤션(코드 스타일/에러코드/응답 포맷)을 따랐는지
확인한다.

## 결과 문서화
결과는 QA(10단계)와 합치지 않고 별도 파일로 즉시 문서화한다:
`docs/domain/{도메인명}/{이슈번호}-{도메인명}-{간략한 제목}-code-review.md`. 형식/작성
규칙은 [code-review-template.md](./code-review-template.md)를 따른다(심각도 이모지,
번호, 문제 상세, 해결 방안 2가지 이상 등).

## 🔌 CI 리뷰 봇과의 관계
이 격리된 자체 점검은 CI에 붙이는 자동 리뷰 봇(CodeRabbit 등)과 목적이 겹치지만 서로
대체 관계는 아니다. 두 겹을 다 쓸지 정하는 기준은
[adapters/review-bot.md](../adapters/review-bot.md) 참고.
