# API 디자인 원칙

출처: [How We Design Our APIs at Slack](https://slack.engineering/how-we-design-our-apis-at-slack/)
— 새 엔드포인트를 설계할 때([branch-workflow.md](./branch-workflow.md) 2단계 기획서 작성 시)
아래 6가지 원칙을 반드시 검토한다. 기획서의 "리스크 및 고려사항" 절에 이 원칙에 어긋나는
부분이 있다면 명시적으로 남긴다.

## 1. 한 가지를 잘하기 (Do one thing and do it well)
- 엔드포인트 하나는 하나의 구체적인 사용 사례만 책임진다. 여러 목적을 한 응답에 욱여넣지 않는다.
- 이슈 1개당 엔드포인트 1~2개로 범위를 좁히는 기존 [issue-template.md](./issue-template.md)
  관례와 같은 방향이다 — 범위가 넘치면 이슈/엔드포인트를 분리한다.
- 컬렉션을 반환하는 응답은 개수를 제한하거나 페이지네이션하도록 설계한다(4번 참고).

## 2. 빠르게 시작할 수 있게 하기 (Fast and easy to get started)
- 기획서에 요청/응답 예시(JSON)를 반드시 포함해, 문서만 보고도 바로 호출해볼 수 있게 한다.
- 에러 케이스도 예시와 함께 명시해 처음 연동하는 사람이 실패 상황을 예측할 수 있게 한다.

## 3. 직관적 일관성 추구 (Strive for intuitive consistency)
- 이 저장소 안에서: 경로(`/api/v1/{도메인}`), 요청/응답 필드 네이밍(camelCase), 공통 응답
  래퍼, 에러 코드(`{DOMAIN}_NNN`) 네이밍을 항상 기존 도메인과 동일하게 맞춘다 — 이미
  🔌 [adapters/code-style.md](../adapters/code-style.md)에서 요구하는 "기존 컨벤션 재사용"
  원칙과 같다.
- 업계 표준과의 일관성도 고려한다: REST 동사(GET/POST/PATCH)와 상태 코드
  (200/201/400/401/403/404/409/500)를 의미에 맞게 사용한다.
- 약어/축약어보다 명확한 이름을 쓴다(`customerUserId`처럼 의도가 드러나는 이름 O, `cid`
  같은 축약 X).

## 4. 의미 있는 오류 반환 (Return meaningful errors)
- 이 저장소의 예외 처리 패턴(커스텀 예외 클래스 + 에러 코드)을 그대로 따른다 — 에러 코드와
  함께 사람이 읽고 바로 원인을 알 수 있는 메시지를 준다.
- 하나의 에러 코드가 서로 다른 원인을 뭉뚱그리지 않는다. 원인이 다르면 코드를 분리한다
  (예: "날짜가 과거" vs "이미 시작 시각이 지남"을 같은 `ORDER_001`로 묶더라도 메시지로
  구분하듯, 최소한 메시지 수준에서는 구분되어야 한다).
- 전역 예외 처리기가 처리하지 못하는 예외는 전부 `500`으로 뭉개진다 — 새 엔드포인트가
  기존에 없던 예외 유형을 유발할 수 있는지 구현 중 반드시 확인한다.

## 5. 확장성과 성능 고려 (Design for scale and performance)
- 컬렉션을 반환하는 API는 설계 시점에 페이지네이션 여부를 명시적으로 결정한다("이번 범위에는
  넣지 않는다"고 결정했다면 기획서에 그 이유와 함께 리스크로 남긴다 — 안 적고 넘어가지 않는다).
- 컬렉션 안에 컬렉션을 중첩해서 반환하지 않는다(예: "채널 목록 + 각 채널의 멤버 전체"를 한
  응답에 담지 않는다) — 필요하면 별도 엔드포인트로 분리한다.
- 무제한 검색/조회처럼 오남용 소지가 있는 엔드포인트는 최소 검색어 길이, 속도 제한(rate
  limit) 등을 검토하고, 이번 범위에 넣지 않기로 했다면 그 판단도 기획서에 남긴다.

## 6. 하위 호환성 유지 (Avoid breaking changes)
- 기존 응답 필드를 제거하거나 타입/의미를 바꾸지 않는다. 필드를 추가하는 확장은 항상 안전하다.
- 부득이하게 깨지는 변경이 필요하면(응답 `id`의 의미를 내부 PK → 외부 코드로 바꾸는 등),
  기획서에 "기존 클라이언트에 미치는 영향"을 명시적으로 적고 검토 시 반드시 짚는다.
- 초기 단계 프로젝트(아직 실제 클라이언트가 붙지 않은 상태)라면 당장의 영향은 제한적이지만,
  원칙 자체는 지금부터 습관화한다.

## 마스터 기획서 재검토
- 도메인 전체를 다루는 마스터 기획서(`docs/domain/{도메인}/1_*.md`)가 있어도, 그 문서가
  개별 엔드포인트에 대해 내린 판단(특히 인가/보안 관련)을 새 이슈에 검토 없이 그대로
  베끼지 않는다. 마스터 기획서는 **작성 시점의 스냅샷**이라, 그 이후 같은 도메인에 추가된
  실제 구현(예: 형제 엔드포인트가 새로운 인가 방식을 쓰기 시작한 것)과 더 이상 일치하지
  않을 수 있다.
- 특히 확인할 것: 같은 컨트롤러/서비스 안의 **다른 메서드와 패턴이 일관되는지**. 마스터
  기획서가 제시한 방식이 그 자체로는 틀리지 않았더라도, 이미 구현된 형제 엔드포인트와
  시각적으로 어긋나면(예: 한 메서드만 인가 애노테이션이 없음) 리뷰어가 매번 "빠뜨린 건가?"
  의심하게 되고, 나중에 누군가 실수로 잘못 "고칠" 위험이 생긴다 — 이것도 하나의 결함으로
  취급한다.
- 재검토 결과 마스터 기획서와 다르게 가기로 하면, 그 이유를 이슈별 기획서에 남긴다(마스터
  기획서 자체를 매번 고치지는 않는다 — 마스터 기획서는 최초 설계 의도의 기록으로 남기고,
  실제 최신 판단은 이슈별 기획서 + 코드가 기준이 된다).

## API 설계 프로세스(Slack 원문, 참고용)
Slack은 기획서 작성 → 내부 리뷰(#api-decisions 채널) → 조기 파트너 피드백 → 베타 테스팅
순으로 진행한다. 이 저장소의 [branch-workflow.md](./branch-workflow.md) 2~6단계(기획서 작성
→ 검토 요청 → 검토 → 수정 → 검토 종료)가 같은 역할을 한다 — 별도 프로세스를 새로 만들 필요
없이, 기존 워크플로우의 기획서 검토 단계에서 위 6원칙을 체크리스트로 쓴다.
