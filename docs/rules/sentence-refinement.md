# 문장 다듬기 규칙 (Sentence Refinement Rules)

> 출처: [toss/technical-writing](https://github.com/toss/technical-writing) — "Step 3. 문장 다듬기" 챕터를 기반으로,
> 이 AI 에이전트 워크플로우 하네스(코드 주석 / 기획 문서 생성)에 맞게 재구성함.
> 원본 라이선스: CC BY-NC-SA 4.0 (Viva Republica, Inc.)

이 문서는 AI 에이전트가 코드 주석과 기획 문서를 작성/리뷰할 때 따라야 할 문장 규칙이다.
5개 원칙 + 체크리스트로 구성되며, 각 체크리스트 항목은 Don't → Do 형태로 구체적인 수정 지침을 포함한다.

---

## 적용 범위

- **코드 내 주석**: Javadoc, 인라인 주석, PR 설명, 커밋 메시지
- **기획 문서**: 기능 명세, 워크플로우 문서, ADR(아키텍처 결정 기록), 이슈/티켓 설명

두 영역 공통으로 아래 5원칙을 적용하되, 코드 주석에는 6번째 원칙(코드 주석 전용)을 추가로 적용한다.

## 원칙 1. 문장의 주체를 분명하게 하기

기술 문서/주석을 읽고 행동하는 주체는 **개발자**다. 도구·라이브러리·시스템을 주어로 쓰지 말고, 개발자가 무엇을 할 수 있는지를 중심으로 쓴다.

### ✅ 도구나 기술, 시스템을 행동의 주체로 사용하지 않는다

| Don't | Do |
|---|---|
| 이 라이브러리는 데이터베이스 초기화를 수행해요. | 이 명령어를 실행하면 데이터베이스를 초기화할 수 있어요. |
| 이 코드는 API 요청으로 인증 토큰을 추가해요. | 이 코드를 사용하면, API를 요청했을 때 자동으로 인증 토큰을 추가할 수 있어요. |

단, 도구/기술 자체의 **동작 원리**를 설명할 때는 도구가 주어가 될 수 있다.
(예: "Impression 로그는 두 가지 방식으로 동작해요. 1. 특정 접근성 요소가 화면에 나타나면 자동으로 수집돼요.")

### ✅ 능동형으로 표현한다

| Don't | Do |
|---|---|
| 애플리케이션이 실행되기 전에 설정이 완료되어야 합니다. | 애플리케이션을 실행하기 전에 설정을 완료하세요. |
| 변경 사항이 적용된 후 다시 빌드되어야 합니다. | 변경 사항을 적용한 후 다시 빌드하세요. |

## 원칙 2. 필요한 정보만 남기기

한 문장에는 하나의 생각만 담는다. 메타 담화(말에 대한 말)는 정보 밀도를 낮추므로 제거한다.

### ✅ 문장을 짧고 간결하게 유지한다

| Don't | Do |
|---|---|
| 버튼을 클릭하면 다음 단계로 이동하게 되며, 그 이후의 작업을 진행할 수 있습니다. | 버튼을 클릭하면 다음 단계로 이동합니다. 이동 후 이어서 작업을 진행하세요. |
| 이 API를 호출할 때 요청 헤더를 포함해야 하며, 올바른 인증 정보를 제공해야 정상적으로 응답을 받을 수 있습니다. | 이 API를 호출할 때 요청 헤더와 인증 정보를 포함하세요. |

### ✅ 메타 담화를 최소화한다

제거 대상 표현 3종:
1. 흐름 설명: "다음으로", "앞서 설명했듯이", "이제 알아보겠습니다"
2. 불필요한 강조: "사실은", "솔직히 말하면", "결론적으로"
3. 독자 반응 유도: "아시겠지만", "여러분도 아실 것입니다"

| Don't | Do |
|---|---|
| 앞에서 설명했지만, 결론은 이 설정을 변경하는 것이 가장 효과적인 방법이라는 겁니다. | 이 설정을 변경하는 것이 가장 효과적인 방법입니다. |
| 아시다시피, 이 설정은 성능에 영향을 줍니다. | 이 설정은 성능에 영향을 줍니다. |

## 원칙 3. 구체적으로 쓰기

모호하거나 장황한 표현은 즉각적인 이해를 방해한다. 아래 6개 항목을 특히 지킨다.

### ✅ 명사 대신 동사를 사용한다

동사에서 파생된 명사("설정 수행", "검토 진행")는 의미를 흐린다.

| Don't | Do |
|---|---|
| 코드 최적화 진행 후 배포 수행이 필요합니다. | 코드를 최적화한 후 배포하세요. |
| MongoDB 연결 정보 설정 및 초기화가 필요합니다. | MongoDB에 연결할 호스트와 포트를 설정하고 데이터베이스를 초기화합니다. |

### ✅ 모호한 표현 대신 명확한 표현을 사용한다

'가능성이 있다', '일부 경우', '필요할 수도 있다' 금지. 확실한 정보만 제공한다.

| Don't | Do |
|---|---|
| 설정 파일을 변경하면 기존 설정이 영향을 받을 수도 있습니다. | 설정 파일을 변경하면 기존 설정이 삭제됩니다. |
| 일부 브라우저에서 정상적으로 동작하지 않을 가능성이 있습니다. | Internet Explorer에서는 정상적으로 동작하지 않습니다. |

### ✅ 누가·무엇을·어디에·어떻게 하는지 생략하지 않는다

| Don't | Do |
|---|---|
| 파일을 업로드하면 자동으로 저장됩니다. | 사용자가 파일을 업로드하면 서버에 자동으로 저장됩니다. |
| 에러가 발생하면 로그를 확인하세요. | 에러가 발생하면 애플리케이션 서버에서 에러 로그 파일(`/var/log/app/error.log`)을 확인하세요. |

예시: "인증 실패 시 에러를 반환합니다" → "비밀번호 인증에 5회 연속 실패하면 `AuthService`가 `ErrorCode.AUTH_LOCKED`를 반환합니다."

### ✅ 실제 동작을 이해할 수 있게 쓴다

업계 은어(예: "던진다" = throw)는 문맥에 따라 다르게 읽힐 수 있다. 실제 동작을 드러내는 표현을 쓴다.

| Don't | Do |
|---|---|
| 에러가 발생하면 Exception을 던집니다. | 에러가 발생하면 예외(`Exception`)를 일으킵니다. |

### ✅ 구체적인 수치나 기준을 제시한다

'많을 때', '빠르게' 같은 표현은 문맥 의존적이다. 숫자로 대체한다.

| Don't | Do |
|---|---|
| 데이터가 많을 때는 성능이 저하될 수 있습니다. | 데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다. |

예시: "락 대기 시간이 길면 타임아웃됩니다" → "`@Lock(PESSIMISTIC_WRITE)` 대기 시간이 3초를 넘으면 `PessimisticLockException`이 발생합니다."

### ✅ 참조되는 내용의 맥락을 설명한다

변수·설정값을 재사용할 때 어디서 정의했는지, 어디서 쓰이는지 밝힌다.

| Don't | Do |
|---|---|
| 1. API 키를 생성합니다. `apiKey` 변수에 저장합니다. ... 3. `apiKey`로 API 인증을 수행합니다. | 1. API 키를 생성하고 `apiKey` 변수에 저장합니다. 이 키는 3단계에서 API 인증에 사용됩니다. ... 3. 1단계에서 저장한 `apiKey`로 인증합니다. |

## 원칙 4. 자연스러운 표현 쓰기

### ✅ 불필요한 한자어를 제거한다

'수행하다', '실행하다', '진행하다'는 대부분 빼도 의미가 전달된다.

| Don't | Do |
|---|---|
| 로그 파일을 삭제하는 작업을 수행합니다. | 로그 파일을 삭제합니다. |

### ✅ 번역체 표현을 자연스럽게 고친다

영어식 명사형(-tion, -ing, -ment) 번역투를 동사 중심으로 바꾼다.

| Don't | Do |
|---|---|
| API 키를 이용한 사용자 인증 처리가 완료된 후, 데이터베이스 접속 설정 진행이 가능합니다. | API 키로 사용자를 인증한 후, 데이터베이스에 접속하도록 설정할 수 있습니다. |
| 시스템 모니터링 수행을 통해 서버 성능 측정 작업을 실시하게 됩니다. | 시스템을 모니터링해서 서버 성능을 측정합니다. |

## 원칙 5. 일관되게 쓰기

### ✅ 공식 기술 용어를 따른다

위키피디아 및 공식 문서 표기를 기준으로 한다. 대소문자 주의.

| Don't | Do |
|---|---|
| K8을 사용하면 애플리케이션 배포가 쉬워집니다. | 쿠버네티스(Kubernetes)를 사용하면 애플리케이션 배포가 쉬워집니다. |

예시: "JPA", "Flyway", "Redis" 표기를 문서 전체에서 통일하고 한글 음역 혼용(예: "제이피에이")을 금지한다.

### ✅ 같은 개념을 여러 방식으로 표현하지 않는다

| Don't | Do |
|---|---|
| 파일을 추가하려면 '파일 선택'을 클릭... 파일을 첨부한 후... 파일을 다시 넣을 수 있습니다. | 파일을 업로드하려면 '파일 선택'을 클릭... 파일을 업로드한 후... 파일을 다시 업로드할 수 있습니다. |

예시: `verificationTicket`을 "인증 티켓", "검증 티켓", "확인 티켓"으로 혼용하지 않고 문서 전체에서 "인증 티켓"으로 통일한다.

### ✅ 약어는 먼저 풀어쓴 후 사용한다

괄호 안에 전체 이름, 약어-괄호 사이는 붙여쓴다.

| Don't | Do |
|---|---|
| 이 기능은 SSR을 지원합니다. | 이 기능은 SSR(Server-Side Rendering)을 지원합니다. |

### ✅ 외래어 표기는 사용 빈도를 고려한다

맞춤법보다 업계 관용 표기를 우선한다(구글 트렌드 기준 5배 이상 많이 쓰이면 관용 표기 채택).

| Don't | Do |
|---|---|
| 프런트엔드 | 프론트엔드 |

## 원칙 6. 코드 주석 전용 규칙 (원 가이드 미포함, 이 하네스가 보충)

toss/technical-writing은 문서 작성에 초점을 맞추고 있어 코드 주석 특유의 문제는 다루지 않는다.
아래는 위 5원칙을 코드 주석에 적용할 때 추가로 지켜야 할 규칙이다.

### ✅ 코드가 "무엇을" 하는지가 아니라 "왜" 하는지를 설명한다

코드를 그대로 옮겨 적는 주석은 정보량이 0에 가깝다.

| Don't | Do |
|---|---|
| `// count를 1 증가시킨다` | `// 동시 요청 시 락 경합을 줄이기 위해 원자적 증가 연산을 사용한다` |

### ✅ TODO/FIXME에는 담당자 또는 조건을 명시한다

| Don't | Do |
|---|---|
| `// TODO: 나중에 수정` | `// TODO(담당자명): 결제 PG사 확정 후 PaymentGateway 구현체 교체` |

### ✅ 자명한 내용은 주석으로 남기지 않는다

Getter/Setter, 명확한 변수명으로 대체 가능한 내용은 생략한다. 원칙 2(필요한 정보만 남기기)의 연장선이다.

### ✅ 예외적인 동작·제약 조건은 반드시 명시한다

원칙 3(구체적으로 쓰기)에 따라 수치·조건을 포함한다.

| Don't | Do |
|---|---|
| `// 재시도 로직` | `// Redis 연결 실패 시 최대 3회, 200ms 간격으로 재시도한다` |

## AI 에이전트 적용 지침

기능 구현 워크플로우 하네스에서 이 규칙을 적용할 때:

1. **생성 단계**: 코드 주석/기획 문서를 처음 작성할 때부터 위 6원칙을 적용한다.
2. **리뷰 단계**: 기존 문장을 검토할 때, 각 문장이 원칙 1~6 중 무엇을 위반하는지 명시적으로 태깅하고 Do 예시 형태로 교정안을 제시한다.
3. **모호성 우선순위**: 원칙 3(구체적으로 쓰기)의 "모호한 표현 금지"와 "수치 제시"는 특히 API 명세·에러 코드 정의·락 타임아웃 등 정확성이 안전성에 직결되는 문서에서 최우선으로 적용한다.
4. **용어집 연동**: 원칙 5(일관되게 쓰기)는 프로젝트의 API 문서·용어집, 도메인 용어(예: 필드명, 상태값 이름)와 대조해 용어 통일 여부를 자동 검사한다.
