# 코드 리뷰 결과 문서 템플릿

[branch-workflow.md](./branch-workflow.md) 9단계(코드 리뷰) 결과를 문서화할 때 이 형식을
따른다. 파일 위치: `docs/domain/{도메인명}/{이슈번호}-{도메인명}-{간략한 제목}-code-review.md`
(QA 결과(`-QA.md`)와 분리 — 코드 리뷰는 구현 직후, QA는 그다음 단계라 시점이 다르고, 파일이
섞이면 "코드 정적 분석으로 찾은 것"과 "실제 동작 검증으로 찾은 것"이 뒤섞여 가시성이 떨어진다).

## 형식 규칙
- **정렬**: 발견 사항은 심각도 내림차순(Critical → High → Medium → Low)으로 정렬하고, 전체
  문서에서 하나의 연속된 번호를 매긴다(섹션마다 번호를 새로 시작하지 않는다).
- **심각도 이모지**: 🔴 Critical, 🟠 High, 🟡 Medium, 🟢 Low — 제목 줄에 번호와 함께 붙여서
  훑어보기만 해도 심각도 분포가 한눈에 들어오게 한다.
- **각 항목 구성**:
  - 제목: `N. {이모지} {심각도} — 한 줄 요약`
  - **문제**: 무엇이 왜 문제인지 구체적으로 — 재현 시나리오, 영향 범위(어떤 요청/데이터에서
    발생하는지), 관련 코드 위치(`file:line`)를 포함한다. "~할 수도 있음" 수준으로 뭉뚱그리지
    않고, 실제로 어떤 입력/상황에서 어떤 결과가 나오는지 구체적으로 쓴다.
  - **해결 방안**: **최소 2가지 이상** 제시한다. 각 방안마다 "무엇을 하는지"뿐 아니라
    장단점(비용, 부작용, 이 프로젝트 컨벤션과의 정합성)을 같이 적어 트레이드오프를 비교할 수
    있게 한다. 방안을 나열만 하고 비교가 없으면 이 형식을 지킨 게 아니다.
- 발견 사항이 전혀 없으면 "Critical/High/Medium/Low 없음"이라고 명시하고, 무엇을 확인했는지
  (리뷰 범위/방법)를 남긴다 — "문제 없음"이라고만 쓰고 끝내지 않는다.

## 예시

### 1. 🟡 Medium — `GET /{code}`의 무관한 사용자 403 경로가 통합 테스트로 커버되지 않음

**문제**: `OrderDetailAuthorizationTest`(`src/test/java/.../OrderDetailAuthorizationTest.java`)는
인증 없음(401)만 확인한다. 소유권 기반 403(주문자 본인/담당 매니저/`ADMIN` 중 누구에도
해당하지 않는 인증된 사용자가 조회 시도)은 `OrderServiceTest.GetOrderDetail.rejectsUnrelatedUser`
라는 서비스 단위 테스트로만 검증된다. 실제 인가 애노테이션/필터 체인/JSON 직렬화까지 거치는
end-to-end 경로에서는 이 케이스가 한 번도 실행되지 않는다.

**해결 방안**:
1. 실제 DB에 사용자/주문 픽스처를 만들어 통합 테스트를 추가한다 — 가장 확실하지만, 이
   프로젝트에 아직 소유권 레벨까지 검증하는 픽스처 기반 통합 테스트 선례가 없으면 새 테스트
   패턴을 도입하는 비용이 든다.
2. QA 단계에서 실서버로 수동 재현해 결과를 QA 문서에 남기는 것으로 대체한다 — 비용은
   낮지만 이후 회귀가 생겨도 자동으로 잡히지 않는다.

## 반영 시점
- 코드 리뷰 직후(9단계)에 작성한다. QA(10단계)를 시작하기 전에 이 파일이 먼저 존재해야
  한다 — QA 중 코드 리뷰 지적 사항을 실서버로 재확인하는 경우 이 파일의 항목을 참조해서
  QA 문서에 "N번 항목 재확인" 식으로 연결한다.
